## 二、三張動畫證據截圖
1. Anticipation — 揮砍預備：角色姿勢已有準備動作，但以整體戰場比例觀看，武器輪廓不夠突出。這不只是影格數量問題，也與姿勢剪影及畫面比例有關。
2. Contact — 命中：命中時已有貼身攻擊、白色受擊效果、傷害數字與血條變化，建立了可辨識的因果反饋。白色閃光偏亮，容易與暗色手繪人物脫節。
3. Recoil — 受擊後座：雙方已拉開距離，騎士姿態與預備階段有差異。但單張照片還不足以證明受擊重量感，必須結合連續影片判斷角色後退、姿勢變化及節奏。

這三張截圖能證明動畫有不同姿勢與階段，不能單靠它們證明連續播放自然。 這是本次視覺驗收的重要界線。

## 三、程式與動畫資產審查
### 1. Manifest 與共用動畫介面 — PASS（適合進入 Phase B）
shared-anim/manifest.json 已定義角色尺寸、腳底 pivot、原生朝向、每幀時長、接觸幀、動畫事件及 Reduced Motion 行為。
- 角色：Thoma、Knight A、Knight B
- Runtime 影格：21 張；Thoma 揮砍 6 幀；騎士受擊／受阻 各 3 幀／角色
- 畫布與 pivot：512×512、(256,464)
- Contact：Swing frame 3；Hitstop：80 ms；Reduced Motion：使用 frame 0、3、5；鏡頭：1.5× 攻擊時放大

這個設計有一項值得肯定的特點：React 與 Godot 可以共用動畫資料，不必共用渲染實作。
但也有架構限制。Manifest 同時包含角色影格、VFX、鏡頭與遊戲情境設定，容易讓動畫素材契約與引擎行為互相綁定。
建議 Phase B 將資料區分為：
- Shared contract： 影格、pivot、方向、時間、事件。
- Presentation policy： 鏡頭、hitstop、震動、特效。
- Scenario fixture： 初始位置、阻擋狀態、預期戰鬥事件。
不一定要立即拆檔，但要避免 React 實作只是逐字模仿 Godot 的播放流程。

### 2. Hitstop 實作 — PASS（原 P1 可以結案）
Test source 的 test_whole_frame_hitstop_and_ui_progress_over_real_hold() 不只檢查角色是否停止，還比較：動畫影格與影格時鐘；World tween 位置；Particle processing；Camera offset、zoom 與位置；Damage number 位置及透明度；HUD 在世界停止時是否仍能更新。
此外，Phase A 文件回報 60fps 影片的第 34–38 幀完全一致，相當於 83.33ms 的固定畫面。
實際渲染的普通播放測得 hitstop 約 90–91ms，截圖讀回則曾讓接觸停頓延長至約 122ms。Codex 保留了失敗記錄，且沒有直接放寬驗收門檻，這點合理。
這可以支持「本次指定的 World 停頓機制修好」，但不等於未來整個遊戲所有節點都已正確分類為 World 或 HUD。

## 四、暗色奇幻手繪風格是否合格？
我的判定是：風格方向合格，動畫資產品質尚未達正式製作品質。
- 場景視覺一致性 82/100
- 角色與背景融合 70/100
- 武器與動作一致性 55/100
- UI 與戰場融合 40/100
以上為三張實際畫面的主觀美術評估分數，不是自動化測試成績。

場景的草地、河道、石橋、車輛及植被大致具有同一套色彩語言。暗綠、赭黃、灰藍與石材褐色的搭配，比常見高飽和 AI 奇幻素材更克制。
不過，角色資產仍有容易產生 AI 拼接感的風險：多張獨立生成的姿勢可能改變布料皺褶、裝備位置與人物比例。SOURCES.md 顯示六張 Thoma 動畫均採單次生成，且沒有剔除不合格幀的紀錄。這證明了來源可追溯，不證明每幀符合角色一致性品質門檻。
另一個問題是畫面主次。現在玩家的注意力很容易被漂亮的整片地景吸引，卻沒有足夠強的視覺線索把注意力集中到「Thoma 這一擊造成什麼戰術結果」。
這比單純增加動畫特效更值得修正。

## 六、Phase B：React vs Godot A/B
建議進入，但必須控制比較變因。
目前沒有足夠證據說 Godot 一定比 React 更適合 Campaign Forge。
Phase B 應該回答的是：在相同素材與戰鬥行為下，哪個引擎能以較低的維護成本，產生更可靠、更自然的戰鬥演出？
建議固定以下比較條件（React 與 Godot 皆相同）：動畫影格：同一組 21 張；Manifest：同一版本及 hash；場景與起始位置：相同；命中／傷害／擊退事件：相同 fixture；Hitstop：同等停頓語意；錄影：60fps，1280×720；Reduced Motion：相同規格。
兩者都必須測量連續畫面的節奏、動畫幀時間、接觸事件一致性、輸入鎖定正確性，以及實作與修改成本。
另外，不應只問觀眾「哪個比較好看」，因為同一套 placeholder 圖片很可能讓兩者都不好看。應分別評估動作節奏、打擊感、角色可讀性與畫面整體感。
建議 Phase B 的決策原則：
- 若兩者畫面與手感接近，優先保留成本較低、能重用現有戰術系統的方案。
- 若 Godot 的動畫時間軸、攝影機與 VFX 明顯更穩定，才值得進一步評估移植。
- 若兩者都不理想，先修動畫素材，不應把美術問題誤判為引擎問題。
