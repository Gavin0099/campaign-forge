| 音效與打擊感                    | 音效產生和觸發可確認。 `impact_synth.gd` 有 0.24 秒合成音效；沒有真實聽感或音訊裝置驗收                               |
| Reduced Motion            | 所宣稱的主要效果有實作。 仍然保留 180 ms wind-up、85 ms lunge 階段的等待，只是移動幅度歸零；不代表整段演出立即完成                |
| 720p／1080p 畫面驗證           | 擷取記錄支持。 但不代表各解析度下的文字、點擊區域、可讀性已完成真人驗收                                                   |
| 演出皆小於 1.7 秒               | 記錄支持本次執行環境。 不應推廣成所有裝置的效能保證                                                             |

比較值得改善的是事件播放器的結構。像下面這段：

```
var damage: Dictionary = result.events[1]
var displacement: Dictionary = result.events[2]
```

對三事件 Spike 是合理簡化，但正式版若新增護盾、暴擊、反擊、免疫或多次命中，就可能失去穩定性。

結論：交接報告沒有重大造假跡象，但「事件驅動」和「打擊感 PASS」都只能在本次 PoC 範圍內成立。

理想方向：武器與人體姿態共同表達力量，而非只靠粒子與閃光。

目前機制示意：全身角色平移、旋轉、閃光與位置變化，缺少武器軌跡。

從上傳畫面可以明確看出以下問題：第一張的白色閃光把人物輪廓蓋住，玩家無法辨識攻擊武器究竟碰到哪裡；第二張的 `−2` 與擊退落點能表達結果，但不能展示力量如何傳遞；第三、四張的阻擋與反彈在靜態畫面幾乎要靠文字解釋才知道發生了什麼。

第五張 Reduced Motion 仍能呈現傷害，這對資訊保留是正面的。第六張 1080p 的場景美術本身有不錯的地形深度，但人物相對地景過小，UI 與場景也像兩個獨立的產品。

### 最值得優先修改的一件事

不要再增加更多閃光或 Camera Shake。先實作真正可讀的揮擊與受擊動畫。

建議以同樣 Thoma、同樣騎士、同樣背景，僅替換角色動作：至少讓身體重心、武器弧線、接觸姿態、被擊中後的失衡能夠連續呈現。

這一項比再增加十種粒子更有可能解除「人物像紙片滑動」的感覺。

## 5. 是否值得遷移到 Godot

### 技術比較

| 面向                      | 保留 React / Canvas   | 遷移 Godot                            |
| ----------------------- | ------------------- | ----------------------------------- |
| 規則測試                    | 現有 TypeScript 測試可保留 | 需移植與驗證等價性                           |
| Tween／動畫                | 可實作，但需建立專用演出層       | 有內建 Tween、節點、動畫工具                   |
| 粒子／震動／特效                | Canvas、WebGL 等可以支援  | API 整合相對直接                          |
| 素材重用                    | 現有網頁素材直接沿用          | PNG 能重用，場景接線需重做                     |
| 敘事 Ink                  | 現有 JS 路線較自然         | 需先驗證 GDScript 相容路線                  |
| Codex／Claude／GPT Review | 易於文字 Diff 與瀏覽器自動化   | GDScript 可 Review，但視覺驗證需 Godot 執行環境 |
| 長期 2D 戰鬥工具              | 需要自行維護整合層           | 編輯器與動畫工具較完整                         |

Godot 的優勢是真實存在的，但它主要節省的是動畫工具與引擎整合成本，不會自動替你產生優質角色動畫或美術設計。

### 10–19 工程天的估算

交接將其拆成規則驗證 2–4 天、戰鬥操作與畫面 4–7 天、測試與匯出 2–4 天，以及 Ink 相容性 2–4 天。

我認為這可以作為研究預算，但不適合當成正式遷移工期承諾。因為其中沒有包括角色美術正式化、完整故事與存檔、在地化、可用性驗收，以及真實的遊戲戰鬥內容轉換。

尤其 Ink 是值得提前解決的架構風險。GodotInk 的 .NET 相依性與目前 GDScript-only 限制不吻合；inkgd 的 Godot 4 分支則不能因為有分支存在就視為已驗證可用。兩者在這次 Spike 都沒有實際接入。

### 遷移前應採取的證據門檻

- 同一套素材、攻擊規則和動畫，在 React 與 Godot 各做一次，盲測哪個打擊感更好。
- 用真實的 Ink 情節資料驗證文字顯示、選項、變數、外部函式及存讀檔。
- 讓 Codex 在乾淨環境中重新匯入、執行 GUT 與自動擷取，確認既有 AI Review 工作流程仍然有效。

我的判斷是：不要因為當前 React 打擊感不足，就直接推論必須換 Godot。 現有 React 原型缺少真正攻擊事件，本來就不是公平的引擎比較。

### 最終裁定

這次 PoC 可以結案，但 P010 不應改成 ADOPT。

技術實現和交接證據已足夠支持下一輪實驗；欠缺的不是更多測試數量，而是令人信服的動作美術、真實玩家感受，以及相對於 React 的可歸因改善證據。

現在最合理的投入，是完成一個「角色真的揮劍、敵人真的承受一擊」的短動畫，然後再決定引擎，而不是提前投入 10–19 工程天的遷移成本。
